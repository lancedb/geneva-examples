## backfill

Filling a UDF-backed **column** of an existing table: register the UDF binding
with `add_columns`, then compute values for the rows. In these docs "backfill"
always means a column fill; filling a materialized view is a *refresh*. The
shared orchestration is `backfill_column` in `geneva_examples/core/backfill.py`;
see [docs/concepts/backfills.md](../concepts/backfills.md).

## blob column / take_blobs

A Lance blob column stores large binary values out-of-line, so a scan can return
cheap *descriptors* instead of the bytes. `take_blobs(ids=...)` then reads the
actual bytes for specific row IDs — how `chunk-videos-openvid` pulls each video
on the worker without the bytes ever passing through the client. See
`geneva_examples/examples/video/chunkers.py` (`chunk_blob_video_udtf`).

## checkpoint_size vs max_checkpoint_size

The same `--checkpoint-size` flag maps to two different geneva knobs: remote
backfills get `checkpoint_size` (seeds the initial adaptive checkpoint size),
local backfills get `max_checkpoint_size` (the adaptive upper bound, which also
caps read-batch size). See
`geneva_examples/core/backfill.py:88-111` and
[docs/reference/local-mode.md](local-mode.md).

## chunker

A `@geneva.chunker`-decorated generator UDF: one input row in, zero or more
output rows out (a video becomes N clips). Geneva only runs a chunker inside a
materialized view, so chunk steps create a view rather than backfilling a
column. The three byte-source variants live in
`geneva_examples/examples/video/chunkers.py` and `chunkers_uri.py`.

## console script

The `uv run <name>` entry point for a step, generated by `build_command` from
the step's spec and wired through `[project.scripts]` in `pyproject.toml`. There
are 21 of them (plus 5 non-generated operator entry points — `tui`, `stats`,
`jobs`, `cleanup`, `udf-studio` — for 26 `[project.scripts]` entries in total);
the TUI runs steps by invoking these same scripts as subprocesses. See
[docs/concepts/spec-and-cli-generation.md](../concepts/spec-and-cli-generation.md).

## CPU pool / GPU pool

Enterprise node groups. `use_cpu_only_pool=True` requests a custom Ray resource
that only CPU-only node groups advertise, keeping no-GPU appliers off the GPU
nodes; geneva checks the UDF's `num_gpus` first, so the flag never holds GPU
work back. It is remote-only — local Ray advertises no such resource. See
`geneva_examples/core/backfill.py:88-99`.

## driver / worker

The **driver** is the client process running the CLI/TUI: it connects, creates
tables, registers UDFs, and submits jobs. A **worker** is a remote Ray actor in
the Geneva runtime executing the UDF. Distinct from the *deployed Geneva driver*
— the process running inside the Geneva runtime on the cluster, whose package
versions the pins in `pyproject.toml` must match (see
[docs/operations/version-pins.md](../operations/version-pins.md)). UDF modules
are not importable on workers
— only the manifest's pip packages exist there — which is why every UDF nests
its imports in the closure. See
[docs/authoring/writing-udfs.md](../authoring/writing-udfs.md).

## example / step / param

The three spec objects in `geneva_examples/core/spec.py`. An `Example` is one
end-to-end pipeline (images, video, pdf, audio, debugging); a `Step` is one
runnable stage with a `run(cfg, **params)` callable; a `Param` is one tunable
that renders as both a CLI flag and a TUI form field. The registry in
`geneva_examples/examples/__init__.py` is the single source both front-ends
render from.

## job record / event list

The geneva-owned record of one backfill/refresh job, stored in `geneva_jobs`.
Its append-only `events` list is the only log a job exposes — there is no
streaming API, so `uv run jobs tail` polls it. Field-level rendering (with
defensive `getattr` fallbacks) lives in `geneva_examples/core/jobs.py`; the
field list is in
[docs/reference/tables-and-schemas.md](tables-and-schemas.md).

## local mode / enterprise mode

**Local mode**: an on-disk Lance database at `local_db_path`, compute on a local
Ray instance, no secrets, `config.yaml` optional. **Enterprise mode**: LanceDB
Cloud (`db://…`) plus the remote Geneva runtime; requires `lancedb_api_key`,
`lancedb_region`, and `geneva_host`. Every divergence is concentrated in
`geneva_examples/core/common.py`; see
[docs/getting-started/configuration.md](../getting-started/configuration.md).

## manifest

The pip-package + environment bundle a remote worker installs before running a
UDF (`GenevaManifest.create_pip(...).pip(...).build()`), built per run with a
unique name suffix. In local mode `build_manifest` returns `None` — local Ray
workers share the driver's environment. See
`geneva_examples/core/common.py:236-248` and the generated pin matrix in
[docs/reference/worker-runtime-pins.md](worker-runtime-pins.md).

## materialized view

A table produced by `conn.create_udtf_view(...)` over a source table and a
chunker, filled by *refresh*. In this repo the clips table **is** the view —
there is no separate copy. Synonyms you may see in geneva itself: *UDTF view*,
*chunker view*; these docs always say "materialized view". See
`geneva_examples/examples/video/chunk.py` and
[docs/concepts/materialized-views.md](../concepts/materialized-views.md).

## modality

`Example.modality` is a free-form string that does not affect execution. Its
only consumer is the docs generator (`geneva_examples/docs_gen/render.py:296`),
which renders `**Modality:** <value>` on each example page; neither the TUI nor
UDF Studio reads it. The live value set is
`image`, `video`, `pdf`, `audio`, and `demo`
(`geneva_examples/examples/*/__init__.py`).

## pointer rows / external refs

A **pointer row** stores a reference to media rather than the media itself, so
nothing heavy transits the driver. Two forms exist here: a Lance blob pointer
(`openvid_rowid`, read on the worker via `take_blobs`) written by
`ingest-videos-openvid`, and **external refs** (`video_uri` + `size_mb`, streamed
on the worker from the assets bucket) written by `ingest-videos-external`. Both
contrast with the inline-bytes shape, where the table holds the MP4 itself.
Column-level detail:
[docs/reference/tables-and-schemas.md#videos](tables-and-schemas.md#videos).

## refresh

Filling or updating a **materialized view** from its source table
(`view.refresh(...)`, or `refresh_async` under `--detach`). "Refresh" is used
only for views; filling a column is a *backfill*. See
`geneva_examples/examples/video/chunk.py:120-129` (synchronous) and
`geneva_examples/examples/video/chunk_external_video.py:196-207` (`refresh_async`
under `--detach`, enterprise only).

## reset vs incremental

The two `backfill_column` modes. `reset=True` (the helper's default) drops and
recomputes the whole column — destructive, but guarantees it reflects the
current UDF. `reset=False` fills only `<column> IS NULL` rows, reusing the
column's originally registered UDF — swapping models therefore requires reset.
Only `frame-embed`, `synthesize-audio`, and `transcribe-audio` expose `--reset`;
every other feature step recomputes destructively on each run. See
`geneva_examples/core/backfill.py:39-57` and
[docs/concepts/backfills.md](../concepts/backfills.md).

## skip_on_error

A geneva `on_error` policy: a failing row is written as NULL and recorded in
`geneva_errors` instead of failing the job, so the job can finish `DONE` with
holes. The debugging example uses it deliberately
(`geneva_examples/examples/debugging/faulty.py:42`); see
[docs/workflows/debugging-failed-rows.md](../workflows/debugging-failed-rows.md).

## stable row IDs

A Lance table option (`new_table_enable_stable_row_ids`) that makes row IDs
survive compaction/update/delete. Write-time only — no migration exists. A
materialized view can only refresh across source versions when its source has
them, so every example table this repo creates passes the option unconditionally
(`OPT_STABLE_ROW_IDS`, `geneva_examples/core/common.py:159-175`).

## storage bucket / assets bucket

Two independent credential sets with deliberately no fallback between them. The
**storage bucket** (`s3_*` / `azure_*` config keys) holds the LanceDB data files
and feeds the connection's `storage_options`. The **assets bucket**
(`assets_s3_*` keys, `ASSETS_S3_*` worker env) holds raw media that the
external-refs video steps enumerate and stream. See
`geneva_examples/core/config.py` and
[docs/reference/environment-variables.md](environment-variables.md).

## system tables

`geneva_jobs` and `geneva_errors`: geneva-owned tables in the connection's
system namespace (`geneva_errors` is append-only; `geneva_jobs` updates each
job's row in place). `table_names()` never lists them; the TUI probes
them via `conn.system_namespace` and labels them `(system)`
(`geneva_examples/tui/app.py`). Field lists:
[docs/reference/tables-and-schemas.md](tables-and-schemas.md).

## task_size vs source_task_size

`task_size` is rows per read task on a **backfill** and is honored in both modes
(`geneva_examples/core/backfill.py:80-87`). `source_task_size` is its analogue
on a view **refresh**: source rows per expansion task. `chunk-videos-external`
tunes it so each video's decode can fan out to its own worker task
(`geneva_examples/examples/video/chunk_external_video.py`; defaults in
[docs/reference/cli/video.md#chunk-videos-external](cli/video.md#chunk-videos-external)).
